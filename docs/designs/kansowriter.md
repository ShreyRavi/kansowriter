# Design: Kansowriter, a quiet place to write (and letters that write themselves)

## Problem Statement
Most writing tools interrupt the writer with badges, counts, suggestions and presence indicators. Kansowriter is a local-first editor that acts like paper. The interface hides while you type. A 2 px line fills toward a daily word goal. Every setting lives in a ⌘K palette. Drafts never leave the device: there's no account and no backend. It runs on the web at writer.kansoboard.com (Vercel) and later as a Tauri 2 desktop app.

Visual source of truth: the design canvas https://claude.ai/code/artifact/61e1a888-3e5b-4d01-9354-d3cfe088ebbe (titled "Calm Writer"; rename every occurrence to Kansowriter). It has 8 artboards: Landing, Editor (chrome hidden / revealed / night), Library sidebar, Command palette, Mobile, and a Tokens and behaviors sheet.

## What Makes This Cool
**Letters that write themselves.** A draft can be sent to someone close as a single link. The recipient opens it and watches the words appear at the writer's real pace, with the pauses, and with the sentence the writer typed and deleted. Then it settles into the finished page. The whole letter, edit history included, sits compressed in the URL fragment. Kansowriter's server never sees it and nothing is uploaded, but the link itself is the letter: it lives wherever the link is kept (R25). Replay exists in writing-research tools (Inputlog, WMX), but I found no consumer product that sends a replay as a personal letter.

## Constraints
- No backend and no network calls at runtime (fonts are self-hosted). The web build is a static SPA on Vercel.
- Stack: React + Vite + TypeScript, CodeMirror 6, Tauri 2 later.
- v0 builds every screen in the design, web only. v0.1 adds letters and replay. Tauri desktop comes after.
- The look comes from the design tokens: Newsreader (writing) and Instrument Sans (UI); paper ground #F5F0E6 / ink #272320 / accent #5E6E3A; night ground #1B1917 / ink #E8E1D5 / accent #B5BF86; radii 3/4/6 px; 44 px touch targets; 18 px icons at 1.5 stroke.

## Premises (agreed)
1. Recording starts in v0. Every draft keeps its edit history from the first keystroke, so drafts written before letters ship can still be replayed.
2. The editor is CodeMirror 6, with drafts stored as plain Markdown. Tiptap was dropped because the design's signature behavior (Markdown syntax visible only on the caret line) is a poor fit for ProseMirror, according to [its maintainer](https://discuss.prosemirror.net/t/show-markdown-syntax-in-editor/382). CodeMirror has `codemirror-markdown-hybrid` for exactly this.
3. "No network calls" means Newsreader and Instrument Sans are bundled (both OFL), not loaded from Google Fonts. The app works offline as a PWA.
4. The sender previews exactly what the recipient will see before a link exists, and chooses "with replay" (the default) or "final text only". Replays show deleted text, so the sender has to consent to that knowingly.
5. Distribution: static Vercel deploy now; Tauri 2 desktop builds from GitHub Releases later. Storage sits behind an adapter interface from day one.

## Approaches Considered
- **A: Straight build.** Text in IndexedDB with a side log. Rejected because text and log can drift, which breaks letter replay, and Tauri would need a storage refactor.
- **B: Layered core with text plus a side log.** Rejected because it has the same drift risk, only behind a cleaner interface.
- **C: Log as the source of truth.** Chosen.

## Recommended Approach: C, an event-sourced draft with a layered core

**Draft model.** A draft = `{id, title, createdAt, snapshots[], ops[]}`, stored in IndexedDB as three object stores (R15): `drafts` `{v: 1, id, createdAt, updatedAt, meta: {title, excerpt, words}, sessions[]}` (title lives only in `meta`), `ops` keyed `[draftId, seq]` (one append-only row per KOP op), and `snapshots` keyed `[draftId, opIndex]` `{text}`. A flush appends only new op rows in one transaction; loading reads the latest snapshot plus the ops after it with one key-range query. Decorations are computed for the visible viewport only, to hold the typing budget. Text = latest snapshot + the ops after it, applied in order. Snapshots are taken every 500 ops and on close. Ops are never deleted, because they are the replay.

**Op format (app-owned, KOP v1).** Kansowriter owns the op format. CodeMirror's serialization is never stored. All lengths and positions in KOP v1 are **UTF-16 code units** (the unit JavaScript strings and CodeMirror use). Golden fixtures include surrogate pairs (emoji) and combining sequences, so any later decoder, including a Rust one in Tauri, must match exactly. An op is `[dt, d, ...runs]` (R18): `dt` is ms from the end of the previous op to the start of this one, `d` is ms this op took to type (0 for single edits), both integers, and each run is a non-negative int `n` (retain n chars), a string `s` (insert s), or a negative int `-n` (delete n chars). The runs must cover exactly the document length before the op. `core/kop.ts` encodes and decodes with no CodeMirror dependency. The `editor/` recorder converts a `ChangeSet` to KOP using `iterChanges`. In v0 the format is "v1-draft": nothing leaves the device, so an IndexedDB version upgrade may still migrate stored ops. It freezes at the v0.1 ship gate, after the Assignment; from then on golden-fixture tests lock v1, and a later v2 adds a decoder, never changes v1 (R19). Consecutive single-character typing ops less than 1 s apart within the same word are merged into one op before storage, with timing kept per word. Phone autocorrect and IME composition replaces inside the current word join the same pending op (R22).

**Single writer per draft.** A draft can be edited in one tab or window at a time, enforced with the Web Locks API (`navigator.locks.request('draft:<id>')`). A second tab opens the draft read-only, showing a quiet "Open here instead" action that hands over the lock. The current writer flushes and releases it, then the new tab reloads from storage. If the holder hasn't released within 2 s (a frozen or discarded tab), the new tab requests the lock with `{steal: true}`; the old tab, if it wakes, has its writes rejected and goes read-only (R23, R5). Every op appended to storage carries the log length it was based on, and storage rejects an op whose base isn't the current head. A property test covers two writers racing. If storage ever rejects a tab's op, that tab goes read-only, reloads the draft from storage, and shows a quiet banner offering "Copy unsaved text" with the rejected insertions (R5).

**Words today (drives the footer count and ProgressLine).** Counting uses the document, not the inserted fragment. For each op, delta = wordCount(affected paragraphs after the op) − wordCount(the same paragraphs before), using the footer's word splitter. Partial-word inserts, fixing a letter inside a word, and typing a space that splits one word into two (or deleting one that joins two) all count by how the document's word count actually changes. Across all drafts, a running balance B adds every delta since local midnight. **Words today = the highest B reached today.** It never drops, and these rules follow:
- Typing a word then deleting it: the typing raised the peak, so it still counts.
- Cut then paste (moving text): −N then +N brings B back to where it was, so the net is zero.
- Retyping text you deleted doesn't count again until B passes its earlier peak.
- A paste of new text counts its words.
Days are bucketed in the timezone the device had when the op was written, using each session's stored offset. The total lives in a `days` store keyed by local date `{B, peak, resetOffset}`, updated in the same IndexedDB transaction that appends ops; a BroadcastChannel message after each commit updates other tabs. It is the source of truth and is never rebuilt from ops, so Clear history and Delete draft leave today's count unchanged (R20). "Reset today's count" in the palette stores an offset; it doesn't edit ops. Property tests cover partial words, in-word corrections, space splits and joins, and cut then paste.

**Sessions.** A session is a run of ops with no gap longer than 30 minutes. The draft record stores `sessions: [{opIndex, at (absolute epoch ms), tzOffset}]`, with a new entry appended only when an op arrives after the draft was opened or after a gap of more than 30 minutes, so opening a draft without typing never creates an empty session (R16). An op's absolute time = its session's `at` plus the sum of `dt` from that session's first op, so locating a boundary never requires summing from the draft's creation.

**Layers (`src/`):**
- `core/`: pure TS, no React or DOM. Draft reducer, snapshotting, word counting (counts words added today, so deleting text doesn't reduce progress), `StorageAdapter` interface, `letter/` codec (encode/decode).
- `storage/`: `IndexedDbAdapter` (Dexie), with ops batched every 500 ms to match the design's autosave debounce. The 500 ms batch writes only closed ops; `visibilitychange` to hidden, `pagehide` and lock handover first close any pending merged typing op, then write. The close snapshot is best-effort (R4, reopened by OV2). `TauriFsAdapter` comes later.
- `editor/`: CodeMirror 6 extensions: hybrid Markdown (syntax only on the caret line), focus dimming (muted color on every paragraph except the caret's, with an optional sentence mode), typewriter scroll (caret line held at 40% of the viewport), a recorder that turns transactions into ops, and the chrome-fade signal (fades 3 s after the first keystroke, comes back on mouse move, tap or Esc, over 200 ms).
- `ui/`: React components that map to the artboards: `Landing`, `EditorShell` (header, footer count, `ProgressLine`), `LibrarySidebar` (340 px, search, draft rows), `CommandPalette` (620 px, 120 px from the top, groups Appearance / Focus / Goal / Document; Document also gets "Clear history (keep text)", which confirms, snapshots the current text as the new base and deletes older ops, snapshots and sessions while keeping today's word count (R9)), and mobile layouts as breakpoints rather than a separate app. Tokens are CSS custom properties on `:root` and `[data-theme=night]`. The theme follows `prefers-color-scheme`, with ⌘⇧N overriding it and the choice saved locally.

**Letters (v0.1).** Encode: ops (or the final text only) → JSON → `CompressionStream('deflate-raw')` → base64url → `writer.kansoboard.com/l#v1.<payload>`. Opening the link decodes it on the client and plays it in a reader view: a caret moving at real pace, pauses longer than 4 s capped at 1.5 s, characters of a merged word spread evenly across its recorded typing duration `d`, with `dt` replayed as the pause before it (R12, R18), and no controls until the reader touches the screen, which reveals a quiet scrubber and a "skip to the end" option. A letter encodes a range of history the sender chooses in the preview: by default, from the start of the draft's last session that contains ops (see Sessions) to now, with a "start replay from" handle that snaps to session boundaries or any earlier point. **Letter payload v1 = `{v: 1, baseText, ops, meta?}`** (R24: `meta` is an optional object of optional fields, first `writtenAt` and `tz`; the decoder ignores unknown keys inside `meta` and rejects unknown top-level keys): `baseText` is the document text at the chosen start, empty if the range begins at the draft's creation, and `ops` are the KOP ops after it. The reader shows `baseText` instantly as the opening page, then replays the ops. The send preview shows the same thing, so the sender sees exactly which earlier text appears without replay. The preview also says: "Anyone with this link can read the letter. It lives in the link, in your chat and in browser history." (R25) `baseText` counts toward the size gate. "Final text only" means `baseText` = the final text and `ops` = [].

**Fallback for oversized letters.** If the encoded link is over the threshold (8 KB to start; tuned by measurement, see Success Criteria), the preview first suggests trimming the replay range or sending "final text only", which almost always fits. If the sender still wants the full replay, they download a `.kansoletter` file (the same compressed payload) and send it as an attachment. The recipient opens writer.kansoboard.com/l, which with no fragment shows an "Open a letter file" button (a file input that works on iOS and Android, picking from Files or Downloads) and a drag-and-drop zone on desktop. The installed PWA also registers `file_handlers` for `.kansoletter`; this works only in Chromium desktop browsers, so phone recipients always use the "Open a letter file" input (R1). The file path is a rare fallback: the main path is the link, kept small by trimming.

**Decoder hardening (links and files are untrusted input).** Reject payloads over 256 KB encoded (one shared constant: the send preview enforces the same cap for links and `.kansoletter` files and suggests trimming when over it (R13)); stop decompressing at 2 MB output or 200,000 ops. Validate the version prefix and the KOP schema, and check that each op's runs exactly cover the current document length before applying it; any violation stops decoding and shows a calm "This letter couldn't be opened" page. Replay runs in timed chunks, so it can't hang the tab. If the browser lacks `DecompressionStream`, the reader shows "Open this link in Safari, Chrome or Firefox to read it" with a Copy link button (R14). Letter content is rendered with the same Markdown decoration as the editor, never through `innerHTML`, so raw HTML shows as plain text. Decorations are text-only in both editor and reader: headings, emphasis, lists, quotes and links (links are not clickable in the reader); image syntax stays literal text, and math and mermaid are disabled, so no letter can make the browser load anything (R6).

**Reuse:** `@codemirror/*`, [`codemirror-markdown-hybrid`](https://cdn.jsdelivr.net/npm/codemirror-markdown-hybrid@1.2.2/README.md) v1.2.2, MIT (if it can't be limited to text-only decorations per R6, fall back to the [codemirror-rich-markdoc](https://github.com/segphault/codemirror-rich-markdoc) approach: a custom decoration extension that hides syntax away from the caret line), Dexie, `cmdk` for palette filtering and keyboard navigation (styled to the design), and the native `CompressionStream`.

### Editing settings in the palette (19A)

- Choice rows (Typeface, Hide interface when typing: Never / After 3 s / After 10 s): Enter cycles to the next option; → opens an inline list of options under the row (↑/↓ to pick, Enter to choose, ← or Esc to close).

## Open Questions
1. **Safari storage eviction.** In Safari, script-written storage for a site that isn't installed can be cleared after 7 days without a visit. Mitigations: call `navigator.storage.persist()`, prompt the user to install the PWA, and show a quiet "Export all" reminder in the sidebar footer (the design already has the link). Is that enough, or should v0 also offer a File System Access folder on Chromium? **Decided for v0 (R10):** call `navigator.storage.persist()` on the first draft; in Safari when not installed, show one dismissible sidebar line "Add to Home Screen to keep drafts safe"; "Export all" shows "last exported N days ago" once N is 7 or more. The File System Access folder idea is closed (R29); backup/import (R21) and the Tauri app cover durable files.
2. **Replay pacing.** Real time with long pauses capped at 1.5 s, or a fixed overall length (for example 60 s whatever the draft)? Test it with a real letter.
3. **Paste in the replay.** A pasted block shows up all at once in the replay. Mark it visually, or leave it?
4. **Rich paste.** Should HTML pasted from Docs or Word become Markdown (turndown), or stay plain text in v0?
5. **Log size ceiling.** How big does the op log get for 3,000 words of messy drafting? Measure it before fixing the 500-op snapshot interval and the 8 KB link threshold.

## Success Criteria
- v0: these screens and states ship at writer.kansoboard.com, matching the tokens: Landing; Editor with chrome hidden, chrome revealed, and night theme; Drafts sidebar; Command palette; Mobile editor layout. The Tokens and behaviors artboard is the reference for all of them, not a screen; Lighthouse PWA install works; zero third-party requests in the Network panel; drafts survive a reload and going offline.

## Reviewer Concerns

### R2-1 — consistency (blocking)

**Problem**

> The words-today formula contradicts its own stated rule for moving text. Words added is computed per op as max(0, inserted words - deleted words). A cut is one op (deletes N words, contributes max(0, -N) = 0) and the later paste is a separate op (inserts N words, contributes N). Moving text by cut and paste therefore adds N words to today's count, not net zero as the section claims. Only a single-transaction move (such as a drag) would net to zero.

**Remedy**

> Pick one behavior and make formula and rule agree: either accept that cut-then-paste counts the pasted words (and drop the net-zero claim), or define a mechanism that nets them (for example a running daily balance where deletions offset later insertions within the day, floored so the displayed number never drops, or matching a paste against a recent cut of identical text).

### R2-2 — clarity (blocking)

**Problem**

> Counting words inside each op's inserted and deleted fragments miscounts any op that touches part of a word. Ops are merged only within a word and under 1 s, so a mid-word pause over 1 s splits 'hello' into 'hel' + 'lo' and counts 2 words; correcting one letter inside an existing word (delete 1 char, insert 1 char) counts 1 - 1 = 0 only by luck, while inserting a missing letter counts as a whole new word; typing a space that splits one word into two, or deleting a space that joins two, is counted as 0 by fragment splitting even though the document's word count changed. The footer count and ProgressLine would drift from what the writer actually wrote. The original R1-7 obligation (a rule precise enough to implement for replacements and edits) remains unmet for these cases.

**Remedy**

> Compute words added from the document, not the fragment: for example, words-added = max(0, wordCount(doc after op) - wordCount(doc before op)), evaluated incrementally on the affected paragraph(s) around the change, or count insertions at word-boundary granularity. State how partial-word inserts, in-word corrections, and space splits/joins count, and add property tests for them.

### R2-3 — completeness (blocking)

**Problem**

> A letter whose replay starts mid-history needs the document text at the range start, but the letter payload is still described only as 'ops (or the final text only)'. KOP runs must cover the document length before each op, and the decoder rejects any op whose runs don't cover the current document, so a trimmed op range replayed from an empty document fails decoding. The recipient-visible behavior of the pre-range text (shown instantly at start? hidden?) and its effect on the sender's consent preview are also undefined.

**Remedy**

> Define the letter payload as {v, baseText, ops} (baseText = text at the chosen start, empty when the range starts at draft creation), specify that the reader shows baseText immediately and then replays ops, include baseText in the size gate, and show it in the send preview.

### R2-4 — clarity (blocking)

**Problem**

> 'Current session' determines the default replay range, what deleted text the recipient sees, and whether the 8 KB gate passes, but it is never defined. It could mean since the draft was last opened, since the tab acquired the write lock, since an idle gap of some length, or since the last calendar day. A letter written across two sittings would by default replay only the second sitting under some definitions.

**Remedy**

> Define a session precisely (for example, ops separated by less than N minutes of inactivity, or since the draft was last opened) and state how the session boundary is found from stored ops given that dt is delta-encoded.

### R2-5 — feasibility (blocking)

**Problem**

**Remedy**
